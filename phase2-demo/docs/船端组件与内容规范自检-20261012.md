## 组件与数据现状

|区域|已具备|仍需注意|

用户提到的“维修”在代码中应区分两层：维保计划与建议，以及已经进入待办的检查和维修执行。本轮重点规范上周新增的前者，并核查后者的现有共享结构。

## 本轮本地规范化

1. 新增 src/page-content/maintenance.json，维护三页签、提前建议的五个分析章节、常规计划的三个分析章节，以及关联入口配置。
2. 新增 MaintenanceDossier.vue，负责维保详情展示；DeviceSituation 不再直接拼装整套维保报告和入口。
3. 新增 maintenanceDossier.js，将计划、执行状态、关联待办及效果观察适配为统一模型；SituationReport 接受页签配置。
4. 静态叙述从 JSON 获取；五处受状态影响的段落通过显式 source 名称映射，避免把状态判断塞入 JSON 或执行配置中的任意表达式。
5. 按钮只发出已知动作，由页面白名单处理。展示或读取配置不会自动建立待办，也不会将事项标为已完成。
6. 维持提前建议与常规周期计划的关系、已处理后的观察入口、既有待办关联和三页签信息分工。没有借本次规范化改写业务定义。

验证：11 项自动检查全部通过，生产构建通过；本地浏览器检查提前维保详情的概览、分析依据展示及助手输入区。新增检查覆盖未建立、已关联、执行中、已处理观察等状态，检查配置内容不被调用方修改。

## 93aee39 相比 4620ea5 的非换皮改造

### 1. 展示类型标准化，配置与数据分离

新增消息渲染入口及场景、询问、反馈记录组件。device-overview.json 维护消息顺序、标识、数据源和展开状态，解析器检查非法类型、重复标识与缺失数据源，保留旧消息兼容。

判断：这是可扩展的起点，不是全站完成配置化。适合重复的语义块；不要把每一句话拆一个组件，也不要为所有页面做一个万能渲染器。

### 2. 关注材料成为独立详情

关注事项有独立路由和档案组件，概览负责当前结论与安排，证据负责变化和解释，记录负责时间接续；数据适配复用已有证据与历史。

判断：切分应对应用户问题和阅读任务。长篇事项详情值得拆，船队与单船摘要仍适合连续阅读。不能把这一规则机械套到单船概览。

### 3. 对话从文本展示增加结构化反馈

询问字段支持类型、默认值和校验；反馈提交与动作完成有显式状态。聊天、补充现场信息、建立待办、确认异常、完成维修不是同一动作。

判断：信息结构与状态约束比气泡样式更有价值。但现有场景仍混用历史记录与当前建议，并非全部达到“一问一答、用户动作触发”的目标，岸端仍需逐故事核查。

### 4. 会话管理独立复用

新增按智能体隔离的会话管理，支持历史会话切换、新会话和草稿保留，知识助手也接入管理。

判断：解决上下文混用；目前仍是原型内存能力，不能据此宣称后台持久化、真实智能体调度或跨设备同步已经完成。

### 5. 状态与回归约束增强

关注事项区分待人工、系统跟踪、处理后观察、已结束等状态；新增消息解析、询问校验、动作状态、档案和会话检查。

判断：可迁移的是状态契约和校验方式，而非照搬船端名称。监测证据不充分时必须保留不确定性，不用一次聊天替代确认。

## 岸端下一步自检与预期效果

|优先级|自检项|预期效果|
|---|---|---|
|P0|船队→单船→设备→事项的对象标识和关联待办一致|左侧材料、右侧回答及跳转始终指向同一对象|
|P0|关注、维修、观察、结束、重新排查的状态与动作分离|仅了解情况不会误建待办；修后不稳能接续原事件；稳定收束有明确确认|
|P1|左侧材料与右侧回答共享事实、结论和证据源|修改趋势或进展后两侧同时更新，不出现结论打架|
|P1|按语义复用结论、趋势、时间线、文档、关联入口组件|新增同类故事主要维护数据，减少页面内条件分支|
|P1|船队和单船保持连续摘要，设备事项详情按阅读任务切页签|保留全局判断，一屏掌握重点；深入分析时不堆成长文|
|P1|用户动作携带问题，对应一条回复；推荐追问只有一种样式|没有突然新提示、重复推荐和丢失输入框；追问以了解情况为主|
|P1|案例状态与材料版本分开：待审批／已沉淀，建议生成后仍待审批|不会把“已提建议”误当最终入库；案例仍是知识库的一类材料|
|P2|JSON 的版本、稳定标识、引用源、字段类型与动作白名单校验|内容维护可预测，缺失来源尽早发现，配置不能越权推进流程|

### 岸端故事验收清单

- 系统观察轻微波动：查看窗口、可比工况和趋势，系统更新，不要求无意义人工处理。
- 检测前需人工：显示缺失证据，询问是否建立待办；同意后才关联事件记录。
- 修后稳定：展示连续几天同工况结果，询问是否结束该事项跟进。
- 修后不稳：保留原处置及待办关联，提出重新检查，不能生成孤立的新故事。
- 提前维保未采纳：仅关闭提前建议，常规周期维保保留；需要协助执行时另行确认待办。
- 已有关联待办：先看当前阶段和待补信息，避免再问一次是否建立同一待办。
- 案例提出建议：显示建议和重新生成的材料，仍待审批；确认沉淀后才成为知识材料。

建议顺序：先核对对象和状态，再统一数据源与消息结构，再抽取重复区域，最后审查布局。目标是减少信息冲突与维护成本，并非追求 JSON 文件数量或页签数量。
