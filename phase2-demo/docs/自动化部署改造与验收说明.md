Vue 模板中的静态资源引用和 CSS 中可分析的 `url()` 由 Vite 在构建时转换；运行时生成的地址由本次新增的 `src/services/appUrl.js` 处理。[Vite 相对 base 说明](https://vite.dev/guide/build.html#relative-base)

## 3. 公司配置待补项

### Jenkins

需要公司已有的 `shared-library` 及其 `nodejs.npm()`，并在构建节点提供 Node 24。建议共享库实际执行：

```sh
cd phase2-demo
npm ci
npm run build
```

以上是共享库应执行的等价步骤；Jenkinsfile 已通过 `dir('phase2-demo')` 切换目录，共享库中不要再次重复 `cd phase2-demo`。

`npm ci` 使用已提交的 `package-lock.json` 校验并安装锁定依赖。本地已经验证该安装方式。[npm ci 官方说明](https://docs.npmjs.com/cli/v11/commands/npm-ci/)

### Nexus

当前 `package.json` 没有公司私有 scope 依赖，不需要为了满足模板而新增私有包或启用虚构 registry。

预留模板：`deploy/npmrc.nexus.example`。后续取得实际 scope、Nexus 地址后，由 Jenkins 的受管 npm 配置提供，可通过 `NPM_CONFIG_USERCONFIG` 指向该文件；认证值由 Jenkins Credentials 注入 `NEXUS_NPM_AUTH`。Base64 的用户名密码同样属于凭据，不提交到 Git。

若公司要求全部公共依赖也通过 Nexus，需要同时配置模板中的全局 `registry`，并在公司网络实际执行一次 `npm ci` 验证代理仓库与锁文件下载行为。[npmrc 官方说明](https://docs.npmjs.com/cli/v11/configuring-npm/npmrc/)

## 4. 公司服务器上的后端与数据

前端产物可以由流水线自动构建和发布；完整业务功能还需要常驻 Node 后端。仅上传 `dist` 无法提供账号登录、实时数据读取、人工上报分析、对话保存与定时检测。

建议首期在同一台服务器部署 Nginx 和一个 Node 后端实例：

```text
浏览器 https://公司域名/ship/#/situation
               |
               v
Nginx /ship/ 统一代理，移除 /ship 前缀
               |
               v
127.0.0.1:5173  Node 服务
  ├─ dist                     前端页面与静态资源
  ├─ /api/...                 登录、数据、助手、事件接口
  ├─ .local-data              数据库、账号、事件与定时产物
  ├─ .local-ai                模型配置、会话等运行数据
  ├─ .claude/skills           分析与交互能力
  └─ wiki_rt-flex50           后端检索知识库
```

后端部署时保留完整 `phase2-demo` 应用源文件结构，包括 `server`、`src`、`scripts`、`.claude`、知识库及相关配置。部分后端模块会导入 `src/workflow`，不能仅复制 `server` 和 `dist`。

部署步骤示例（Linux，路径及域名由公司替换）：

```sh
cd /srv/ship-maintenance/phase2-demo
npm ci
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-local.txt
npm run build

export SHIP_PYTHON=/srv/ship-maintenance/phase2-demo/.venv/bin/python
export SHIP_PUBLIC_ORIGIN=https://ship.company.example
export TZ=Asia/Shanghai
export PORT=5173
npm start
```

这是后续部署操作示例，本次未执行。Node 应使用服务器进程管理服务常驻运行。当前应用应先保持单实例；前端静态目录可独立发布，但同一套 SQLite、事件产物和定时作业不能直接按无状态应用随意扩容。

启动前恢复交付包的 `.local-data` 与可独立使用的 `.local-ai/config.json`；服务器没有本机 CC Switch 时使用已经导出的 `source:manual` 配置，并验证服务器能访问模型提供方。上述目录应作为持久运行数据保留，代码更新不能覆盖或删除它们，也不能放入公开的静态资源目录。

`SHIP_DATA_DIR` 可将 `.local-data` 指到持久目录；`.local-ai` 当前仍按应用根目录读取，可以由部署系统挂载或链接到持久目录。更换访问域名后需要重新登录，原浏览器本地存储不会自动迁移到新域名。

Nginx 示例在 `deploy/nginx-ship.location.conf.example`，放入公司已有 `server` 块中。它同时代理前端和 API，关闭响应缓冲以保持流式输出，保留 Host。`SHIP_PUBLIC_ORIGIN` 只填浏览器地址的协议、域名和可选端口，**不包含 `/ship/` 路径**。

`/ship` 需要重定向到 `/ship/`，相对路径才有稳定基准。部署到其他子路径时同步修改 Nginx 的 location 与重定向；前端无需重新构建。后端继续监听 `127.0.0.1`，本示例要求 Nginx 与后端位于同一主机网络空间。[Nginx proxy_pass 与响应缓冲说明](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)

本次没有启动或修改健康分析、异常检测、效果观察的调度逻辑。正式启动后端时，仍按原有规则执行启动检测和后续定时任务。
