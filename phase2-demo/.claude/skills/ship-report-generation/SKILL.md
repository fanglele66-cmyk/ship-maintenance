# 船端报告

使用服务端提供的事件、指定任务、本次 submissionContext、执行结果及必要的知识片段。先对齐任务和提交轮次；恢复后本次确实完成的工作按本次结果记载。把历史事实、本人补充、系统采样和模型推断分开。与本轮无关的对话和未提交草稿不进入报告。

| 调用模式 | 依据与结果 |
| --- | --- |
| submit-report | 船员正式回交后，基于对应 submissionSnapshot 和 executionFacts 起草分析。现场报告已经存在，模型结果补入同一报告。 |
| refresh-report | 只对符合条件的当前任务最新报告重新整理，依据该次原始记录及已确认补充。主程序保留原版与修订历史。 |
| report | 根据本人补充和目标报告原文提出修订草稿。只有报告提交人确认采用且原版本仍匹配，主程序才更新报告。 |

这三个模式的模型回复均为一个 JSON 对象，顶层只有 `summary` 和 `analysis`，见[报告分析示例](template/patch.example.json)。summary 至少 5 个字符，结论和四个小节每项最多 6000 个字符。四节都须有正文：

- evidence 写已经实施的项目、实际观察、读数及单位，只引用本次有记录的事实；仅收到图片元数据时，仅登记附件来源。
- interpretation 说明这些事实支持何种解释、依据是什么。
- unverified 写本次明确未完成、受阻或尚待核实的事项；已完成的核对与尚未得到证实的原因应分别记载。“不适用”表示本轮无需执行。
- next 提供与尚存问题相符的建议，派工、观察与闭环由轮机长决定。

输入含 `preferredDecision` 时，在 `analysis.next` 中优先说明这项安排及对应步骤的依据：

- `repair`：本轮排查已完成并记录异常，首选由轮机长派发维修。范围落在登记异常的项目或部位；原因、读数或具体维修方法尚缺时如实列入待核实项。
- `observe`：本轮维修已完成，首选安排效果观察，跟踪原异常测点在可比工况下是否复现。逐项完成选项就是执行反馈，备注可为空；效果由后续观测验证。

结合执行人本次明确补充和正式记录处理矛盾。若本次有受阻项目、复测失败或异常仍在，以具体事实说明需要优先处理什么。不因缺少选填备注而重复派工。

提交、关联和保存由主程序完成。模型不生成任务身份、报告编号、照片文件、时间戳或业务状态。观察、闭环和上报岸基报告有各自的形成条件，沿用对应入口。正式报告字段、独立文件、照片与版本约定见[归档契约](references/files.md)。
