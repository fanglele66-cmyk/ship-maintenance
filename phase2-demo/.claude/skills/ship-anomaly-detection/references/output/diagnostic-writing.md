# 面向轮机员的排查内容

人工、OEM、AI 事件均由宿主大模型读取本次事件证据和实际知识正文后编写内容候选，再由发布器校验。脚本负责准备证据、校验、补齐系统字段和写入，不从固定脚本、固定话术或模板派生排查任务。缺少合格模型候选时保留准备文件和失败原因，等待重新生成，不发布模板分析。缺少实时数据或未命中算法候选时，应说明证据边界并根据现有事件信息和知识安排核实，不推测尚未取得的现场结果。

## 三级拓扑：候选原因 → 排查方向 → 具体事项

1. 一级 `diagnostic_plans[]` 按已列出的候选原因组织，每个任务通过 `cause_id` 对应一个原因，`schemeTitle` 只写简短中文名词短语，概括候选原因或对象，例如“控制空气泄漏”“1缸温度测量链路”“停机前温度趋势”；不含“排查、检查、核实、核对、验证、确认”等动作词，不写执行句。动作、方法和判断要求放在步骤及事项正文中，任务名称仍由模型结合事件与知识生成，不由脚本删词或拼接。按本次证据选择 2～5 个彼此有区别的任务；不得机械规定物理原因和测量链路各占多少个。
2. 二级 `steps[]` 是同一原因下不同的部件、故障环节、泄漏位置或信号链路等排查方向，每个任务包含 2～4 个方向。`action` 写明该方向及其对象，不能只按“准备、检查、复测、记录”等通用流程阶段拆分，也不能只改标题后重复同一内容。
3. 三级 `inspection_items[]` 说明如何执行该方向。每步由模型按实际需要选择 2～4 个具体操作或检查事项。`title` 是简短事项标题，`content` 是完整执行说明，`item_type` 区分无需选择检查结果的 `operation` 与需要提交检查结果的 `inspection`。新生成内容使用 `content`，不再使用 `question`。

例如，事件涉及空气进口压力，证据和知识支持“控制空气泄漏”这一候选原因时，一级可为“控制空气泄漏”；二级可分别为“检查控制空气管路法兰垫片破损”和“检查管路松动或破损”；法兰方向的三级事项再写实际需要的接近与隔离操作、垫片外观检查、允许条件下的检漏及其结果判断。此例只说明层级关系，不能把空气泄漏或法兰检查复制到其他事件，也不能把尚未核实的垫片破损写成已确认事实。

运行经过、趋势对照和测量链路核实均应服务于具体候选原因。测量链路仍未排除且与事件有关时，明确要验证的传感器、机旁独立仪表或采集环节；不能因为取图列出六个测点就要求六个全部拆检或校验。知识支持不足时列出待核实条件；已排除的方向不另建同义任务。

## 事项内容与结果选项

- `content` 写明当前方向下的具体对象、动作、方法及必要工况；需要结果时写清怎样支持或不支持该原因，以及需记录的读数、单位、时间、照片或记录。工具和操作准备按需融入相关事项内容，不再设置 plan 的 `tools/prerequisites`，也不再设置 step 的 `method/acceptance_criteria/evidence_to_record`。任务整体完成要求仍放在 `completion_criteria`。
- 涉及隔离、泄压、停机或禁止带压拆卸等安全条件时，在 `safety_notes` 中明确。只有本船资料支持且现场条件允许时才安排试验或拆检，不能用生成事项替代实际操作许可。
- `item_type=operation` 用于查阅资料、准备对照、记录等无需选择正常/异常结果的执行事项；不输出 `options/answer_type/required/answer`。若某事项本质上需要判断检查结果，应使用 `inspection`，不能以操作类型绕过结果要求。
- `item_type=inspection` 必须由模型提供两个与本事项判断相符的 `options`，每项结构为 `code/label/abnormal`。`code=normal` 对应 `abnormal=false`，`code=abnormal` 对应 `abnormal=true`；`label` 应写清本事项的正常、异常结果，例如“密封处未见连续气泡”和“密封处出现连续气泡”。选项文字由模型结合事件和知识编写，不由脚本统一替换为泛化标签，也不能与正文判断方向相反。
- inspection 的 `answer_type=single_choice`、`required=true`、`answer=null` 和步骤反馈初值由发布器补齐，模型候选不填写这些系统字段。只有用户提交检查结果后才更新答案。
- 后台可查测点使用本船映射表名称；仅现场可查的项目明确写“机旁检查”或“查阅记录”，不能伪装为在线测点。数值限值、误差、阀位、端子号和部件位置只能来自本船有效资料；未取得资料时说明应查哪份图纸或手册，不编造数值。

不同方向下的事项应有不同对象或验证目的，不复制同一句执行说明凑数。内部 `diag_*`、`cause_id`、`step_id`、采集 key 不进入可见正文；传感器仅使用本船中文显示名称，不拼接英文，常用单位如 RPM 可用于读数。

排查任务的标题、方向、事项内容、结果选项和完成要求中的点位仅使用本船分析映射中的中文 `display_name`，不拼接 `display_name_en`，不以英文名称、内部编码或采集 key 代替中文名称。`pointDataId`、`pointCode` 及采集 key 只用于结构化引用和取数，不得在中文名称后追加“映射点……”或括号编号。对比多个测点时使用中文名称，例如“1缸排气温度至6缸排气温度”，不要写点位编号范围。发布校验若指出内部点位编号，应改为对应中文名称后重试，不改映射表或结构化 ID。现场软件参数有英文原名时，先给出有资料依据的中文含义，必要时括注原名方便查找，例如“关闭死区时间（Closed dead Time）”；不要编造未核实的中文译名。

正文按信息需要完整表达，没有几十字的硬上限。事项标题尽量简短，保留识别对象所需的完整中文名称，正文不为卡片宽度删掉对象、方法和判断依据。2～4 个事项由模型根据每个排查方向的实际需要决定，不按固定脚本生成相同数量和内容。人工上报、AI 周期和 OEM 的生成、发布及消费统一使用当前结构；`question` 和已移除的任务、步骤字段一律拒绝，不保留旧格式兼容分支。

## 主机转速/异常停机示例

先核对“主机转速”的真实样本、上报停机时刻和操作记录。若窗口内读数均为零，只能说明该窗口的记录情况；没有停机前样本，不能描述为已观察到“从运行转速骤降到零”。人工上报进入事件排查，不等于数据已证实设备本体故障。

若证据支持，可按“控制条件未满足”“转速测量链路失真”等候选原因组织任务，再按该原因下的具体环节划分方向，并将核对停机经过、记录或对照读数写入相应事项。涉及控制空气时明确“控制空气压力”；涉及起动过程时才考虑“起动空气压力”。未提供保护停机记录或控制指令时，写明需查阅该记录，不虚构平台存在相应传感器。

## 事件建议

`summary` 只保留简短判断边界和下一步动作。基础信息、取数过程和统计推断分别放在现有事件信息、`analysis_basis` 与 `engineering_inference`。事件概览、排查、维修的生成正文中出现具体传感器时仅使用中文名称，不拼接英文；结构化查询字段和用户反馈原文保持原值。
